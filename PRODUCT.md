## Platform

## Stack

React + TypeScript + Vite + Tailwind in `frontend/` (user's choice, 2026-10-27). Data comes from JSON the Python pipeline exports (`scripts/` → `frontend/public/data/`). React Bits components may be added via the shadcn CLI. Runs locally with `npm run dev` or as a static build.

## Users

1. **Course markers and the viva panel** (UE24AM343AB3, Big Data Systems & Responsible AI, Track G). They are judging whether the project measured real energy, used public carbon data correctly, shifted jobs without missing deadlines, and reported savings and delay honestly. They read the story pages.
2. **The brief's data team**, who run nightly Spark batch jobs and want lower emissions with zero missed deadlines. They use the Tonight view: when each job will run tonight, and why.

## Product Purpose

GreenShift measures the energy of representative Spark jobs and moves flexible nightly jobs into cleaner half-hours of the GB grid, using the public Carbon Intensity API forecast, without missing deadlines. The site explains the method and shows the results (emissions saved against delay added), and plans tonight's schedule from the live forecast.

Success: a marker can follow claim → evidence for every step, and a data-team member can see tonight's plan and the reason behind each delay in under a minute.

## Positioning

The savings come from our own measurements on real hardware (Intel RAPL on an i5-12450H), a real two-year GB carbon record (2024-25, forecast and actual), and a backtest that never misses a deadline. Every number has a source and a stated limitation (average rather than marginal intensity; RAPL covers only the CPU package; laptop rather than cluster).

## Operating Context

- Shown live from a laptop at the viva, possibly offline or on campus Wi-Fi that intercepts HTTPS. The Tonight view fetches the live forecast when it can and otherwise uses the most recent stored forecast, labelled with its fetch time.
- Times: the data and the scheduler work in UTC on a 30-min grid; people read UK local time.
- Terms: carbon intensity (gCO2/kWh), forecast vs actual, release time, deadline, flexibility window, non-interrupting / interrupting policies, gross vs attributable energy.

## Capabilities and Constraints

- Built: carbon data client and cleaning, energy meter (RAPL / model), TPC-DS-derived Spark jobs (99/99 queries run on Spark 4.2), carbon EDA.
- Not built yet: measurement campaign (step 7), scheduler and backtest (step 8), online scheduler (step 9). **Savings, delay and per-job energy figures do not exist yet.** The site shows those sections as pending until the pipeline exports them.
- Nightly window: release 22:00, deadline 07:00 UK local (decided 2026-10-27). Open: the final scale factor (SF5 proposed), whether the live demo launches real jobs.
- Required wording: "Workload derived from TPC-DS; not comparable with published TPC-DS results." Carbon data credit: "Carbon Intensity API, NESO (CC BY 4.0)."

## Product Principles

1. Every number on screen has a source a marker can trace, and a pending state when it does not exist yet.
2. Show the trade-off, not only the win: emissions saved next to delay added, and zero missed deadlines as a hard line.
3. Explain each decision: the scheduler says why a job moved.
4. State limitations where the claim is made, not in a footnote.
5. Works offline at the viva.

## Accessibility & Inclusion
