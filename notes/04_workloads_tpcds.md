# 04: Workloads: TPC-DS on Spark

## Generating data

- TPC-DS current spec: **v4.0.0** (tpc.org). The official tools (`dsdgen`/`dsqgen`) are C sources under the **TPC EULA**.
- We use **DuckDB 2.0's `tpcds` extension**: `CALL dsdgen(sf=…)` and `tpcds_queries()`. The DuckDB docs say its 2.0 generator matches the TPC-DS v4 tools. No compiler is needed, and it runs on Windows.
- Script: [scripts/generate_tpcds.py](../scripts/generate_tpcds.py) → `data/tpcds/sf{N}/*.parquet` (zstd) + `data/tpcds/queries/qNN.sql`.
- SF1: 4.2 s to generate, 24 tables, **0.28 GB** parquet, store_sales 2.88 M rows, inventory 11.7 M.
- Plan: develop on SF1, then **SF5 or SF10** for the real measurements (longer jobs mean less RAPL quantisation error). This follows the brief: "develop on a small sample, then scale up".

## Running on Spark 4.2

- All **99/99** queries run at SF1 (2026-10-27). Times range 0.7 s (q41) to 12.5 s (q14) on local[*].
- Fix needed: 8 queries (q16, 32, 50, 62, 92, 94, 95, 99) use ANSI `"double-quoted"` aliases. In Spark these are string literals, so the loader rewrites them to backticks (`workloads/spark_jobs.py::load_query`).
- Output sink: `df.write.format("noop")` forces full execution with no output I/O and avoids Hadoop `winutils.exe` on Windows (Spark can *read* parquet without it but cannot write).
- Heaviest at SF1: q14 (12.5 s), q72 (10.5 s), q23 (9.2 s), q04 (9.2 s), q78 (7.7 s), q16 (7.0 s), q95 (6.6 s), q67 (6.5 s), q24 (6.4 s).

## "Representative nightly jobs" (proposal: final set after SF5/10 timings)

| Job | Queries | Character | Flexibility |
|---|---|---|---|
| `daily_sales_report` | 3, 7, 19, 42, 52, 55 | light scans + joins, BI dashboards | must finish by 07:00 |
| `customer_analytics` | 4, 11, 74 | heavy multi-year customer aggregation | flexible |
| `inventory_supply_chain` | 21, 22, 37, 39, 72, 82 | inventory joins (q72 is the worst) | flexible |
| `cross_channel_promo` | 14, 23, 33, 56, 60, 77, 80 | union of 3 sales channels, very heavy | flexible, interruptible per query |
| `returns_audit` | 16, 50, 62, 94, 95, 99 | returns & shipping lag | flexible |
| (optional) `ml_segmentation` | MLlib KMeans/ALS on customer features | syllabus tie-in (MLlib) | flexible, interruptible |

Each job = an ordered list of queries. Query boundaries are natural **checkpoints** for the interruptible policy.

## Licence / fair use

- Data generated by dsdgen is synthetic (no personal data). No re-identification issue arises.
- TPC fair-use rule (⚠ read the Fair Use Quick Reference v1.0.0 before submitting): results that are not audited **must not be called "TPC-DS results"**. Use wording like "a workload *derived from* TPC-DS (queries and data generated with DuckDB's tpcds extension); results are not comparable to published TPC-DS results."
